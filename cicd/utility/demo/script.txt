@ Gitsby demo script. This is the readable/editable source for what the demo gif
@ shows. It gets turned into demo-scenario.toml, which gen-demo-gif.py renders.
@
@ How to read it:
@   A bare line is typed on camera, exactly as written.
@   A line starting with # is the caption that introduces each command. It is
@   shown as a shell comment, appearing whole rather than being typed out.
@   A line whose first non-blank character is @ is an editing note and never
@   appears on screen.
@   Indentation is for reading only - it means nothing.
@   Scenes run top to bottom in the order they appear here.
@
@ How to change it:
@   Edit this file. Every change here is carried into demo-scenario.toml in the
@   same pass, so the two never drift.
@   Nothing reads this file automatically - it is not a program. The map at the
@   bottom says which knob each thing here corresponds to.
@
@ Everything the demo runs is real. The commands execute against a throwaway repo
@ built fresh for each render, so the output cannot go stale - but that also means
@ a change here has to keep the repo's state consistent from one scene to the next.


@ •••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••
@ Format
@
@ Gif only, no video: 960x540, 50 fps, silent.   -> assets/demo.gif (README)
@
@ Currently 902 frames, 47.7 seconds, 5.65 MB. There is no size cliff to stay
@ under - the file is committed and served from raw, where the limits are 50 MB
@ (warning) and 100 MB (blocked). GitHub's 10 MB figure is for attachments and
@ Camo's 5 MB is for external images; neither applies. So size is a judgment
@ about load time on a slow connection, not a budget.
@
@ Length is a different matter. The written target is twenty to thirty seconds,
@ and this does not meet it. Five scenes of real output, one of which stops and
@ waits to be answered, come to about 47 seconds with nothing left to trim that
@ would not cost either a scene or the ability to read one. The target was
@ written before the demo had to show the tool asking before it acts. See
@ design.md, which records what the number is now and why it moved.
@
@ What actually costs bytes: about 97% of the file is smooth-scroll frames, and
@ they run ~1.27 MB per extra frame-per-line. Pauses, cursor blink and the held
@ end frames are free - an identical frame stores as no change. So the levers, in
@ order, are the number of output lines, the scroll rate, and the per-scene clear.
@ Read time can be increased freely; it costs nothing.
@
@ What costs seconds is different, and it is mostly typing. Measured on the nine
@ scenes this replaced: captions 12.9s, commands 13.5s, output and scrolling
@ 10.7s, read pauses 24.5s. That is why the captions stopped being typed out -
@ watching narration arrive a letter at a time cost more screen time than the
@ commands it introduced.


@ •••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••
@ The set
@
@ A drawn terminal window on black - title bar, three muted traffic lights, square
@ corners, no shadow. Nothing is screen-recorded; the frames are drawn.
@ Dark warm-gray background, pale green text, gray prompt punctuation, dimmer gray
@ for the captions.
@ The prompt's user@host is picked from a generic list and tinted, seeded so it is
@ the same every run - no real username, hostname or path is ever on screen.
@ The prompt also shows the folder the command runs in. The back half of the demo
@ is about which folder you are standing in, so a prompt that said only "~" would
@ be hiding the thing being demonstrated.
@ The screen is 99 columns wide and a typed line is cut off at the edge, so a
@ caption's budget is 99 minus the prompt - which moves when the folder does. The
@ renderer warns by name when a caption or command would overflow.
@ Font: Monaspace Argon SemiBold, falling back through JetBrains Mono, Cascadia
@ Mono and DejaVu Sans Mono to whatever monospace the system offers. The font is
@ resolved through fontconfig, which is the reason a render is a Linux job.
@ Commands are typed at a human pace - roughly 135-183 wpm, slower on digits, a
@ beat of thought before a -flag, and the occasional typo typed and corrected.
@ Captions are not typed; they appear whole and hold for a moment to be read.
@ The cursor glides between cells rather than jumping, and blinks every 520ms.
@
@ Every scene clears the screen before it starts, as though `clear` had been
@ typed. That is deliberate and is what keeps the file affordable: a scrollback
@ that never accumulates halves how far the view has to travel.


@ •••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••••
@ The world the commands act on
@
@ Built offline before the first scene and thrown away after, and nothing in it
@ touches the network. Everything is generic: a made-up author (Mika Rivers), a
@ throwaway HOME and gitconfig, no real paths.
@
@ Two repos, in two folder trees that differ from their first folder down:
@   ~/dev/github.com/acme-corp/acme-api        the service the first three scenes work on
@   ~/code/github.com/mika-rivers/dotfiles     somewhere else entirely
@ acme-api has a local bare "origin" beside it, one commit, a clean push, and one
@ uncommitted edit waiting in config.yml - so the very first scene has something
@ to show, the branch scene has something to carry along, and the sync scene has
@ something to commit. dotfiles only ever has `account` run in it; what matters is
@ that it is a real repo under a different root.
@
@ A gitsby config file gives each tree its own GitHub account, matched on the
@ folder names "github.com/acme-corp" and "github.com/mika-rivers". The roots
@ differ on purpose: the rule is a run of folder names found anywhere in the path,
@ and two trees sharing a root would not show that.
@ Each account carries a fake token. Nothing reads it - a local-path remote needs
@ no credentials - but its presence is what makes gitsby report the account as
@ applied rather than merely resolved, which is the state a real user is in.
@
@ HOME is the demo root, so "~/dev/..." in the prompt and "/tmp/gitsby-demo/dev/..."
@ in the output are the same place. The identity the accounts set is deliberately
@ not exported into the scenario's environment: an exported GIT_AUTHOR_EMAIL would
@ supply the very thing the folder rules are supposed to be supplying, and the
@ demo would be showing something it had not proved.
@
@ Commit dates are pinned to a fixed value, and the build the demo runs is
@ stamped with the newest release rather than with the commit it was built from.
@ That makes the commit hashes, the version banner, and therefore every line of
@ output and the gif bytes, identical from one commit to the next - which is what
@ lets the pipeline rewrite assets/demo.gif only when the demo really changed.
@ The banner therefore names the last release, not the build in progress.
@ So: keep every commit message and every edit in this file fixed. In particular
@ never demo a bare `sync` with no message - the auto-generated message is a
@ timestamp, and the gif would differ on every render.

@ Scene 2: start the feature, and be asked first
@ Two things at once. The uncommitted edit from the fixture comes along to the new
@ branch instead of being left behind or committed to the default branch. And the

@ Where each knob lives
@
@ Everything in this directory:
@   script.txt            this file - the readable version, edited by hand
@   demo-scenario.toml    the machine version: one [[step]] per scene above
@   demo-repo.bash        builds the throwaway world described under "The world"
@   gen-demo-gif.py       the renderer - the set, typing model and frame rate
@
@ Scene captions, typed lines and hold times are per-step in demo-scenario.toml
@ (note=, show=, pause=). The folder shown in the prompt is cwd=, defaulting to
@ "~". The command that really runs is run=, which is where the -y and the repo
@ setup hide - and which has to enter the same folder cwd= claims.
@ A scene that stops to be answered carries ask= (the text the command waits on)
@ and answer= (what gets typed). That step alone runs with a terminal on its
@ stdin; stdout stays a pipe, so nothing a program saves for a terminal reaches
@ the frames.
@ Captions appearing whole rather than being typed is type_notes = false, set once
@ at the top of the scenario.
@ Canvas size, colors, fonts, typing speed, blink and the 50 fps grid are
@ constants near the top of gen-demo-gif.py. Scroll rate is one of those too
@ (150 px/s), overridable per scene.
@ Which file the pipeline renders, and where the result lands, is set in
@ cicd/config.bash. One engine, one place.
@
@ To re-render: cicd/cicd.bash on Linux, without --quick. It regenerates only if
@ the bytes actually changed - the byte-for-byte contract depends on Linux
@ fontconfig and the pinned optimizer, so nothing else renders one.
